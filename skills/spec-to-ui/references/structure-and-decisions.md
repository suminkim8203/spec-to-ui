# 명세서에서 구조와 결정으로

명세서 해석과 중단 후 재개에 사용합니다. 아래 형식은 필요한 항목만 사용하며 작은 작업에 별도 파일 묶음을 의무화하지 않습니다. 기존 문서 형식이 있으면 따릅니다. 읽기 전용 원본에는 기록도 쓰지 않습니다.

## 접근 범위와 현재 단계

실제로 읽은 문서·개정·절/쪽, 채팅의 확인 턴 범위, 코드 확인 범위를 적습니다. 문서 전체와 최근 채팅 일부를 읽은 경우를 구분합니다. 접근할 수 없는 자료는 제목만으로 보충하지 않습니다. 필요한 도구를 먼저 찾고 정말 없는 맥락만 요청합니다.

첫 응답은 현재 단계, 확인한 목적과 결정, 지금 만들 결과, 결과에 영향을 주는 미정을 짧게 설명합니다. 명세서 정식 승인 여부와 현재 화면을 설계할 충분성은 따로 판단합니다. 모든 미정을 한꺼번에 해소하려고 진행을 막지 않습니다.

## 화면으로 번역하기

1. **핵심 작업:** 역할별로 시작 조건 → 필요한 정보/입력 → 판단/행동 → 성공 결과 → 다음 위치를 연결합니다. 실패·취소·권한 거절의 복구도 필요한 범위에서 정리합니다.
2. **권한:** 역할 × 열람/생성/수정/승인/취소 범위를 명세서 근거로 작성합니다. 화면 숨김과 서버 권한 검증 구현을 구분합니다. 관리자라는 명칭만으로 모든 권한을 부여하지 않습니다.
3. **페이지/영역:** 탐색 위치·공유 주소·작업 맥락이 달라지면 별도 페이지를 검토합니다. 같은 작업의 상세·편집·완료는 패널/화면/모달/인라인 중 근거 있는 초안으로 제안합니다. 기능마다 메뉴를 만들지 않습니다.
4. **상태:** 정상·빈 결과·로딩·오류·입력 검증·권한 부족·완료 등 실제 흐름에 필요한 상태를 찾습니다. 해당하지 않는 상태를 형식적으로 추가하지 않습니다. 변화의 주체와 다음 행동을 연결합니다.
5. **정보 우선순위:** 먼저 판단할 정보, 판단을 돕는 정보, 필요할 때 열 정보로 나눕니다. 각각 어떤 작업을 돕는지 설명합니다. 모든 페이지에 큰 소개 영역이나 요약 숫자를 붙이지 않습니다.

같은 정보를 여러 위치에 배치할 때는 [동일 정보 중복 판단](review-and-handoff.md#information-redundancy)에 따라 각 위치의 추가 역할을 확인합니다.

목록·상세 관계는 [상세의 가치와 이동 기준](composition-and-validation.md#detail-patterns)을 함께 검토합니다. 펼침·일정한 위치의 상세·별도 이동은 조건부 후보이며, 사용자 제안을 선택이나 버튼 삭제 요구로 자동 확정하지 않습니다.

필요하면 다음 표로 추적합니다.

| 요구 근거 | 역할·핵심 작업 | 페이지/상태 | 먼저 볼 정보와 이유 | 행동·다음 결과 | 근거 수준 |
|---|---|---|---|---|---|
| 문서 절/항목 또는 발언 | 누가 무엇을 마치는지 | AI가 제안한 구성도 표시 | 실제 작업과 연결 | 성공·복구와 연결 | 확정 / 사실 / 해석 / 제안 / 미확인 |

기존 ID는 보존합니다. 필요한 경우 짧은 로컬 ID를 붙일 수 있으나 사용자가 정한 요구 ID로 가장하지 않습니다. 여러 화면에 같은 데이터가 보이면 최신 상태·수정 주체의 관계를 확인합니다.

회원가입·초대·이메일 확인·활성화·최초 비밀번호 설정·변경·재설정은 다른 흐름입니다. 명세서에 없는 인증 방식을 고르거나 함수 이름으로 구현을 판단하지 않습니다. UI 초안에서 인증을 다루지 않는다면 불필요한 기술 결정을 요구하지 않습니다.

## 요구 보충으로 연결하기

요구의 누락·충돌이 현재 화면·권한·핵심 흐름을 막으면 [명세서 보충과 복귀](requirements-supplement.md)를 적용합니다. 명세서가 짧다는 이유로 시작하거나 배치 선택·구현 결함을 업무 요구 부족으로 처리하지 않습니다.

## 질문의 기준

`미정 → 어느 화면/행동이 달라지는가 → 지금 필요/나중에 가능 → 권장안과 손실`로 판단합니다. 관련 질문은 묶어서 쉬운 선택으로 안내합니다.

예: 승인제 미정이면 즉시 확정과 담당자 승인은 목록의 상태·행동·완료 안내가 달라집니다. 그 차이를 설명하고 확인합니다. 그동안 공통 일정 정보와 목록 항목은 정리할 수 있습니다. API/DB를 아직 고르지 않았다는 이유로 정적 정보 배치까지 멈추지 않습니다.

## 의도 해석과 실사용 위험 판단

1. **해석에 따라 결과가 달라지는 경우:** 사용자의 표현이 여러 방식으로 해석되고 그 차이가 화면 구조·스크롤·상호작용에 영향을 준다면 기존 대화·이미지·코드를 먼저 확인합니다. 그래도 불명확하면 구현 전에 예상 동작을 짧게 재진술하거나 간단한 도식으로 확인합니다. 중요한 해석을 임의로 확정하거나 가설을 사용자 결정으로 기록하지 않습니다.
2. **위치와 동작의 기준:** ‘고정’, ‘하단’, ‘선택’, ‘자동’ 같은 표현은 무엇을 기준으로 어디에 적용되는지 구체화합니다. 화면·페이지·특정 영역 중 위치 기준, 움직이는 영역과 유지되는 영역, 작동 계기를 구분합니다. 이미 확인된 사항은 다시 묻지 않습니다.
3. **의도가 명확해도 실사용 흐름 예측:** 대표 사용자가 실제 작업을 수행하는 과정을 따라갑니다. 콘텐츠 양·길이, 화면 크기/높이, 반복 조작과 입력 방식이 달라질 때 정보 확인·선택·이동·복귀가 어려워지는지 검토합니다. 요청한 모양의 구현과 실제 작업의 편의성을 각각 확인합니다.
4. **예상 불편을 근거로 설명:** ‘불편할 것 같습니다’로 끝내지 않고 `발생 조건 → 불편이 생기는 이유 → 영향을 받는 작업 → 완화 방법 → 확인할 시험`으로 설명합니다. 실제 관찰과 예상 위험을 구분하고, 예측은 필요한 범위의 시안·조작 시험으로 확인합니다. 검증하지 않은 예측을 사실처럼 단정하지 않습니다.
5. **사용자 판단이 필요한 문제만 확인:** 핵심 작업 방해·요구 간 충돌·큰 구조 변경·중요한 손실이 예상되면 구현 전에 짚고, 의도를 유지하는 보완안과 손실을 제시합니다. 실제 선택이 필요한 변경은 확인 전 확정하지 않습니다. 승인 범위의 사소한 조정은 자율적으로 처리하고 미정에 의존하지 않는 작업은 계속합니다. 사용자가 의도를 명확히 했다는 이유만으로 사용성이 검증됐다고 보지 않으며, 예상 불편을 이유로 다른 구조로 임의 변경하지 않습니다.

## 작은 결정 기록

한 문서의 표로도 충분합니다. 항목/적용 범위, 현재 내용, 상태, 근거 위치 또는 짧은 발언, 위임 범위, 참고/시안 연결, 유지·변경·회피 범위, 영향을 받는 페이지와 다음 판단을 필요한 만큼 남깁니다. 상태는 사용자 확정, 문서/코드 사실, 해석, AI 제안, 미확인, 보류를 구분합니다.

“A의 목록, B의 상세 배치” 선택이면 각각만 기록합니다. A의 색과 B의 글꼴까지 선택했다고 하지 않습니다. AI 위임은 고른 내용과 위임 근거를 함께 남깁니다. 감상·열람·질문 시간 만료는 확정 발언이 아닙니다.

정정은 해당 항목의 새 값과 이전 값의 대체 관계를 남기고 나머지를 유지합니다. 거절·보류를 필수 질문으로 되살리지 않습니다. 재개 시 현재 자료·새 정정·다음 대기 선택을 읽으며 변경과 관련된 구조/참고만 다시 판단합니다. 합성 시험의 응답은 실제 사용자 결정과 다른 기록에 둡니다.
